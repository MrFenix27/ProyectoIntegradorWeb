# Informe de avance para exposición — Requerimiento / Ruta / Descripción

**Proyecto:** ColdTrace / WebIntegrado · **URLs demo:** Front `http://localhost:4200/login` · API `http://localhost:8080` · H2 `http://localhost:8080/h2-console/`
**Accesos:** `admin/admin123` (ADMIN) · `user/user123` (USER) · `guest/guest123` (GUEST) · H2: JDBC `jdbc:h2:mem:coldtrace`, user `sa`, sin contraseña

| Requerimiento | Ruta donde se dio solución | Descripción de lo que se hizo |
|---|---|---|
| 1.1 Entidades de dominio (mín. 3) con relaciones `@OneToMany` / `@ManyToOne` | `src/main/java/com/example/WebIntegrado/model/Producto.java` | Se agregó `@OneToMany(mappedBy="producto") List<Lote> lotes` con `@JsonIgnore` para cerrar la relación bidireccional con Lote sin generar recursión infinita en el JSON. |
| 1.1 Entidades de dominio (mín. 3) con relaciones `@OneToMany` / `@ManyToOne` | `src/main/java/com/example/WebIntegrado/model/Lote.java` | Ya tenía `@ManyToOne producto`; se agregó `@OneToMany(mappedBy="lote") List<RegistroTemperatura> registros` para completar la cadena Producto → Lote → RegistroTemperatura. |
| 1.1 Entidades de dominio (mín. 3) con relaciones `@OneToMany` / `@ManyToOne` | `src/main/java/com/example/WebIntegrado/model/Operacion.java` | La operación guardaba el lote como un `Long loteId` suelto; se agregó la relación real `@ManyToOne Lote lote` sobre la misma columna `lote_id` (solo lectura) para poder hacer joins JPQL sin romper el código existente. |
| 1.1 Entidades de dominio (mín. 3) con relaciones `@OneToMany` / `@ManyToOne` | `src/main/java/com/example/WebIntegrado/model/RegistroTemperatura.java` | Conserva su `@ManyToOne lote` original; ahora es el lado dueño de la bidireccional con `Lote.registros`. Sin cambios de código, solo pasa a formar parte del grafo completo. |
| 1.1 Entidades de dominio (mín. 3) con relaciones `@OneToMany` / `@ManyToOne` | `src/main/java/com/example/WebIntegrado/model/Usuario.java` y `model/Rol.java` | Se crearon la entidad `Usuario` (username único, password cifrado, rol) y el enum `Rol` con `ADMIN, USER, GUEST`; son la base del login y los permisos. |
| 1.2 Configurar BD H2 o MySQL en `application.properties` | `src/main/resources/application.yaml` | Se configuró H2 en memoria (`jdbc:h2:mem:coldtrace`, usuario `sa`, `ddl-auto: create-drop` para que Hibernate cree las tablas desde las entidades y consola H2 habilitada). El `.yaml` equivale al `.properties` pedido. |
| 1.2 Consola H2 visible en Spring Boot 4 | `src/main/java/com/example/WebIntegrado/config/H2ConsoleConfig.java` | Spring Boot 4 eliminó la consola H2 automática (verificado en el jar de autoconfiguración); se registró manual el servlet `JakartaWebServlet` en `/h2-console/*` y se quitó el scope `runtime` al driver H2 en el `pom.xml` para poder compilarlo. |
| 1.3 Repositorios extendiendo `JpaRepository` | `src/main/java/com/example/WebIntegrado/repository/ProductoRepository.java`, `LoteRepository.java`, `OperacionRepository.java`, `RegistroTemperaturaRepository.java`, `UsuarioRepository.java` | Los 4 repositorios existentes ya extendían `JpaRepository`; se mantuvieron y se les sumaron las consultas JPQL, y se creó `UsuarioRepository` con `findByUsername` para el login. |
| 1.4 Servicio con lógica de negocio y CRUD | `src/main/java/com/example/WebIntegrado/service/ProductoService.java`, `LoteService.java`, `OperacionService.java`, `RegistroTemperaturaService.java` | CRUD completo en Producto y Lote (a Lote se le agregó el `actualizar` que faltaba); `OperacionService.registrarRecepcion` concentra la regla de negocio (solo un despacho `EN_TRANSITO` puede pasar a `RECEPCIONADO` y acumula los controles de recepción). |
| 1.5 Validar persistencia con Postman | `docs/ColdTrace.postman_collection.json` | Se amplió la colección de 4 a 16 peticiones (auth, CRUD, filtros JPQL y casos de seguridad). Demostrable: `POST /api/auth/login` → `GET /api/productos` con token devuelve los 3 productos; sin token responde 403. |
| 2.1 Consultas JPQL por fecha, categoría y estado | `repository/ProductoRepository.java` (`buscarPorTipo`, `buscarPorTemperaturaObjetivo`) | JPQL que filtra productos por categoría (`tipo`) y por rango térmico que cubra una temperatura objetivo. Demo: `GET /api/productos?tipo=Biologico` → 1 resultado. |
| 2.1 Consultas JPQL por fecha, categoría y estado | `repository/LoteRepository.java` (`buscarPorEstado`, `buscarVencidosAntesDe`, `buscarPorTipoProducto`) | JPQL por estado, por vencimiento anterior a una fecha y por tipo de producto con `JOIN` a Producto. Demos: `GET /api/lotes?estado=ACTIVO` → 2; `GET /api/lotes/vencidos?antesDe=2026-12-01` → 1. |
| 2.1 Consultas JPQL por fecha, categoría y estado | `repository/OperacionRepository.java` (`buscarPorEstado`, `buscarPorRangoFechas`, `buscarPorTransportista`) | JPQL por estado, por rango de fechas con `BETWEEN` y por transportista. Demo: `GET /api/operaciones/en-transito` → 1. Expuesta además `GET /api/operaciones/por-fechas?desde=…&hasta=…`. |
| 2.1 Consultas JPQL por fecha, categoría y estado | `repository/RegistroTemperaturaRepository.java` (`buscarPorLoteYFechas`, `buscarAlertasPorLote`) | JPQL por lote + rango de fechas y consulta de alertas con doble `JOIN` que detecta temperaturas fuera del rango permitido del producto. Demo: `GET /api/lotes/3/temperaturas/alertas` → 1. |
| 2.2 Operaciones transaccionales con `@Transactional` | Los 4 archivos de `service/` | Se anotó cada servicio: lecturas con `@Transactional(readOnly=true)` y escrituras (`registrar`, `actualizar`, `eliminar`, `registrarRecepcion`) con `@Transactional`, de modo que la recepción de un despacho es atómica. |
| 3.1 Integrar Spring Security | `pom.xml` y `src/main/java/com/example/WebIntegrado/security/SecurityConfig.java` | Se agregó `spring-boot-starter-security` y la cadena de filtros: CSRF desactivado, sesiones stateless, consola H2 y `/api/auth/**` públicos, `GET` para ADMIN/USER/GUEST y el resto de `/api/**` solo ADMIN/USER, con el filtro JWT por delante. |
| 3.2 Sistema de roles y permisos | `model/Rol.java`, `security/SecurityConfig.java` y los 4 controllers | Roles `ADMIN, USER, GUEST` aplicados en dos niveles: matriz URL en `SecurityConfig` y `@PreAuthorize` por método (los `DELETE` solo `ADMIN`; `POST/PUT` ADMIN o USER; `GET` los 3 roles). Demostrable: GUEST lista con 200 pero crear le da 403. |
| 3.3 Seguridad a nivel de endpoints | `controller/ProductoController.java`, `LoteController.java`, `OperacionController.java`, `RegistroTemperaturaController.java` | Cada endpoint lleva su `@PreAuthorize` y se expusieron rutas de consulta sensibles (`/por-fechas`, `/alertas`, `/vencidos`) restringidas a ADMIN/USER. |
| 3.4 `UserDetailsService` desde la base de datos | `src/main/java/com/example/WebIntegrado/security/CustomUserDetailsService.java` | Implementación propia que carga el usuario con `UsuarioRepository.findByUsername` y le otorga la autoridad `ROLE_<rol>`; falla con excepción si el usuario no existe. |
| 4.1 Generar JWT al iniciar sesión | `controller/AuthController.java` (`POST /api/auth/login`) y `security/JwtUtil.java` | El login autentica con `AuthenticationManager` y firma un token con subject = username, claim `rol` y expiración de 24 h (`app.jwt.*` en el `application.yaml`). Demostrable: login `admin/admin123` devuelve `token`. |
| 4.2 Filtro JWT en cada solicitud | `src/main/java/com/example/WebIntegrado/security/JwtAuthFilter.java` | Filtro que en cada request lee `Authorization: Bearer <token>`, lo valida con `JwtUtil` y carga el usuario en el contexto de seguridad; registrado antes del filtro de usuario/clave en `SecurityConfig`. |
| 4.3 Endpoints protegidos con token válido | `security/SecurityConfig.java` | Todo `/api/**` (salvo `/api/auth/**`) exige token: verificado que sin token responde 403 y con token expirado o falso también se rechaza. |
| 4.4 Registro y autenticación | `controller/AuthController.java` (`POST /api/auth/register` y `POST /api/auth/login`) + `dto/RegisterRequest.java`, `LoginRequest.java`, `AuthResponse.java` | El registro valida username único, asigna rol (por defecto USER) con password cifrado en BCrypt y devuelve token inmediato; verificado creando el usuario `profe`. Usuarios semilla (`admin/user/guest`) en `config/DatosIniciales.java`. |
| Extra: el front consume la API con JWT | `frontend/src/app/auth.service.ts`, `auth.interceptor.ts`, `auth.guard.ts`, `login.component.ts`, `app.config.ts`, `app.routes.ts` | El Angular no enviaba token y todo le daba 403; se le agregó login con sesión en `localStorage`, interceptor que adjunta el `Bearer` automáticamente, guard que redirige a `/login` y botón Salir con usuario/rol visible. Demo en `http://localhost:4200/login`. |
| Extra: ruta raíz amigable | `controller/HomeController.java` | `GET /` era 403/404 en el navegador; ahora es público y devuelve el estado de la API con las URLs del front, el login y la documentación. |
| Extra: migración futura a MySQL | `docker-compose.yml`, `src/main/resources/application-mysql.yaml`, `pom.xml` (driver `mysql-connector-j`) | Migración dejada lista sin tocar H2 actual: MySQL 8.4 + phpMyAdmin por Docker y perfil `mysql` (`ddl-auto: update`). Para activarla: `docker compose up -d` y arrancar con perfil `mysql`. |
