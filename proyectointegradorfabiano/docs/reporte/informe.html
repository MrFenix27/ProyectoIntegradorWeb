1Resumen ejecutivo

ColdTrace es una aplicación web para el control de la cadena de frío: registra productos termosensibles, sus lotes y las lecturas de temperatura, y gestiona despachos y recepciones con verificación de condiciones de llegada. El sistema está construido como una API REST en Spring Boot consumida por una SPA en Angular, con autenticación JWT y tres roles (ADMIN, USER y GUEST).

2Arquitectura del sistema

La aplicación se organiza en tres capas desplegadas localmente. El navegador ejecuta la SPA de Angular; cada acción del usuario dispara una petición HTTP a la API REST, que aplica seguridad, validaciones de negocio y persiste en MySQL. La comunicación en desarrollo pasa por el proxy de Angular, de modo que el frontend siempre llama a /api en su propio origen y no existen problemas de CORS.

4Consumo de la API REST

El frontend se comunica con Spring Boot exclusivamente mediante HttpClient. Las llamadas se centralizan en dos servicios: ColdtraceApiService, que declara los endpoints tipados, y ColdtraceStoreService, que mantiene el estado compartido y notifica a las vistas.

4.1 Configuración del cliente HTTP

provideHttpClient registra el cliente y el interceptor funcional de autenticación. El interceptor agrega el token a cada petición salvo las de /api/auth y evita repetir la cabecera en cada servicio. 

// app.config.ts
provideHttpClient(withInterceptors([authInterceptor]))

// auth.interceptor.ts
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  if (req.url.includes('/api/auth')) return next(req);

  const token = localStorage.getItem('jwt');
  if (token) {
    req = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
  }
  return next(req);
};

4.2 Servicio de API

Cada método devuelve un Observable tipado con la interfaz del dominio, de modo que TypeScript detecta errores de forma y campos inexistentes en tiempo de compilación. La base es relativa (/api) para que el proxy de desarrollo resuelva el destino. 

@Injectable({ providedIn: 'root' })
export class ColdtraceApiService {
  private readonly http = inject(HttpClient);
  private readonly base = '/api';

  productos(): Observable<Producto[]>            { return this.http.get<Producto[]>(`${this.base}/productos`); }
  buscarProducto(id: number): Observable<Producto> { return this.http.get<Producto>(`${this.base}/productos/${id}`); }
  registrarProducto(data: Omit<Producto,'id'>)      { return this.http.post<Producto>(`${this.base}/productos`, data); }
  actualizarProducto(id: number, data)              { return this.http.put<Producto>(`${this.base}/productos/${id}`, data); }
  eliminarProducto(id: number): Observable<void>   { return this.http.delete<void>(`${this.base}/productos/${id}`); }

  lotes(): Observable<Lote[]>                      { return this.http.get<Lote[]>(`${this.base}/lotes`); }
  temperaturas(loteId: number)                      { return this.http.get<Temperatura[]>(`${this.base}/lotes/${loteId}/temperaturas`); }
  registrarOperacion(data: Operacion)                { return this.http.post<Operacion>(`${this.base}/operaciones`, data); }
  registrarRecepcion(id: number, data)               { return this.http.put<Operacion>(`${this.base}/operaciones/${id}/recepcion`, data); }
}

4.4 Flujo del token JWT

  1. El usuario envía sus credenciales a POST /api/auth/login.
  2. El backend autentica con AuthenticationManager y firma un token con el username, el rol y 24 h de vigencia.
  3. El frontend guarda jwt, username y rol en localStorage.
  4. Cada petición posterior pasa por el interceptor, que agrega Bearer.
  5. El filtro del backend valida la firma, carga el usuario y aplica las reglas de rol.
  6. Si el token falta o expira, la API responde 401/403 y la app vuelve al login.

4.5 Estado compartido y actualización de la interfaz

Angular 22 usa detección de cambios sin Zone.js. Para que las respuestas HTTP refresquen la vista sin intervención manual, el estado global se expone con signals: los servicios escriben en signal y las vistas leen con computed. Esa decisión fue clave para resolver el problema descrito en 6.1. 

// coldtrace-store.service.ts (resumen)
private readonly lotesState = signal<Lote[]>([]);
readonly lotes = this.lotesState.asReadonly();

recargar(): void {
  this.api.lotes().subscribe({
    next: lotes => this.lotesState.set(lotes),      // notifica a las vistas
    error: err => this.reintentar(() => this.cargarLotes(), err)
  });
}

5.2 Validación cruzada de rango térmico

Además de las reglas por campo, el formulario de producto valida la coherencia del rango. El validador se aplica al grupo completo y marca el campo de temperatura máxima cuando la mínima es igual o mayor. 

function rangoTermico(grupo: AbstractControl): ValidationErrors | null {
  const minima = grupo.get('temperaturaMinima')?.value;
  const maxima = grupo.get('temperaturaMaxima')?.value;
  if (minima === null || maxima === null || minima === '' || maxima === '') return null;
  return Number(minima) < Number(maxima) ? null : { rangoTermico: true };
}

readonly productoForm = this.fb.nonNullable.group({
  nombre: ['', [Validators.required, Validators.minLength(3), Validators.maxLength(60)]],
  temperaturaMinima: [2, [Validators.required, Validators.min(-60), Validators.max(40)]],
  temperaturaMaxima: [8, [Validators.required, Validators.min(-60), Validators.max(40)]],
  vidaUtilDias: [30, [Validators.required, Validators.min(1), Validators.max(3650)]]
}, { validators: rangoTermico });

5.3 Comportamiento de la interfaz

  • El error de un campo aparece cuando el usuario lo tocó o modificó, no al abrir la vista.
  • El borde del campo inválido cambia de color y el mensaje se asocia visualmente a ese campo.
  • Los botones de envío se deshabilitan mientras el formulario es inválido o hay una petición en curso.
  • Al enviar, se marcan todos los campos como tocados para no ocultar errores pendientes.

6Problemas de integración y soluciones

Durante la integración aparecieron fallos que no se detectan compilando: la aplicación levantaba y las peticiones respondían 200, pero la interfaz no reflejaba los datos o los permisos no coincidían. Se documentan los ocho casos más relevantes con su causa y la solución aplicada.

6.1 La interfaz mostraba 0 aunque la API respondía correctamente

SíntomaEl panel principal mostraba “0 lotes” y tablas vacías; en la pestaña de red todas las peticiones tenían estado 200 y el JSON era correcto.
CausaAngular 22 funciona sin Zone.js (zoneless). El estado se guardaba en campos planos dentro de subscribe(), y esos cambios no marcan la vista como obsoleta: la detección de cambios nunca volvía a ejecutarse.
SoluciónSe migró el estado compartido a signals (signal, computed, toSignal). Al actualizar un signal, Angular marca automáticamente las vistas que lo leen. Se verificó con los indicadores (3 lotes) y con la telemetría que se actualiza cada 2 s.

6.2 El rol GUEST recibía 403 en operaciones y el frontend reintentaba sin fin

SíntomaAl entrar como guest, el panel no cargaba operaciones y el navegador repetía la petición cada 1,5 s indefinidamente.
CausaDos reglas inconsistentes: la matriz de SecurityConfig permitía GET solo en productos y lotes, mientras el controlador autorizaba explícitamente a GUEST en operaciones. Además, el store reintentaba ante cualquier error, incluidos 401/403.
SoluciónSe alineó SecurityConfig con @PreAuthorize (GET de operaciones para los tres roles) y el reintento se limitó a errores de red o 5xx, ignorando los 4xx. GUEST pasó a consultar sin errores y sin tráfico repetido.

6.3 No existía vista de detalle ni ruta por identificador

SíntomaEl requerimiento de “lista, formulario y detalle” quedaba incompleto: el detalle solo era posible eligiendo un lote en un desplegable, sin URL propia ni acceso desde la tabla.
CausaEl frontend no consumía GET /api/productos/{id} y no había ruta con parámetro.
SoluciónSe creó ProductoDetalleComponent en /productos/:id, con ActivatedRoute, el método buscarProducto() y el botón Ver en la tabla. La vista compone el producto con sus lotes y lecturas.

6.4 Estilos duplicados y ausencia de SASS

SíntomaTodo el CSS se aplicaba dos veces (import global y styleUrl del componente) y las clases de las vistas hijas dependían de esa copia global; además el requerimiento pedía SASS y solo había CSS.
CausaEl archivo app.css se importaba desde styles.css y a la vez se declaraba como estilo del componente raíz, sin arquitectura de parciales.
SoluciónSe migró a SCSS con tokens, mixins y anidamiento: _tokens, _shell, _components y _login, compilados desde styles.scss. Los estilos compartidos quedaron globales y el componente raíz solo conserva sus custom properties, eliminando la duplicación.

6.5 Credenciales inválidas sin mensaje útil

SíntomaAl escribir mal la contraseña, el login no mostraba un mensaje claro y el usuario no sabía si el problema era la clave o la API caída.
CausaLa excepción de autenticación no estaba manejada y se traducía en una respuesta genérica del servidor.
SoluciónSe agregó un @ExceptionHandler(BadCredentialsException) que responde 401 con un mensaje JSON, y el componente distingue 401/403 (“Credenciales inválidas”) de un error de conexión (“Verifica que el backend esté en localhost:8080”).

6.6 El login aparecía dentro del layout de la aplicación

SíntomaEn /login se veían la barra lateral y el buscador, con enlaces a vistas protegidas antes de autenticarse.
CausaEl componente raíz renderizaba siempre el shell (sidebar + topbar) alrededor del router-outlet.
SoluciónEl shell se condicionó a auth.logueado y se agregó la clase sin-sesion para anular márgenes y relleno. El login quedó a pantalla completa sin duplicar el router-outlet.

6.7 Migración de H2 en memoria a MySQL

SíntomaCon H2 los datos desaparecían al reiniciar el backend, y cualquier cambio de configuración exigía recrear la base. Los tests, en cambio, no debían depender de un servidor externo.
CausaLa configuración usaba una única fuente de datos en memoria (ddl-auto: create-drop) sin perfiles.
SoluciónMySQL 8.4 con Docker quedó como perfil por defecto (spring.profiles.default: mysql, ddl-auto: update, volumen persistente y phpMyAdmin), y se creó application-h2.yaml para pruebas y ejecución sin Docker. El test de contexto usa @ActiveProfiles("h2"), por lo que mvnw test sigue funcionando solo. Se verificó la persistencia creando un producto, reiniciando el backend y comprobando que seguía existiendo.

6.8 Evidencias con barras duplicadas en las capturas

SíntomaLas capturas de página completa mostraban el sidebar y la topbar desplazados o repetidos a mitad de la imagen.
CausaLos elementos con position: fixed se posicionan respecto del viewport; al capturar toda la página, el motor los replica en cada franja.
SoluciónEl script de evidencias inyecta CSS antes de la captura: convierte sidebar y topbar a position: absolute y ajusta la altura del sidebar al documento. Las 12 figuras de este informe se generaron así.
Lección de integración. Los fallos más costosos no fueron de compilación sino de contratos: entre la detección de cambios y el estado, entre la matriz de seguridad y los @PreAuthorize, y entre la configuración de la base y los tests. Verificar con peticiones reales y pruebas de navegador permitió detectarlos y dejarlos cubiertos.
